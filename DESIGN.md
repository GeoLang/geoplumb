# Geoplumb design

Demand-driven geospatial compute engine. A distinct layer from geodukt (batch ETL to files) and fluvius (event streams): geoplumb computes at request time. With nubis it is the planned PDAL replacement.

## Data plane: pull only

The data plane is pull, permanently. A pull names a window (bbox plus target ground resolution). It flows sink to source, each transform rewriting it upstream via `plan`: a kernel widens by its halo, a reproject inverse-projects the bbox and rescales resolution by the local scale factor. Chunks flow back down, each transform producing exactly its requested grid via `compute`.

A pull may also name a time interval (`TimeInterval`, half-open UTC epoch milliseconds). It overrides the interval a time-varying source was configured with, and unlike the window it is not an element's to rewrite: `plan` implementations build their upstream request from the output one (`WindowReq::with_window`) and the engine reasserts the pull's time on whatever comes back, so it reaches every source as the instant asked for. Which nodes it reaches is a capability, not a name check: an element declares `time_varying`, the engine ors it over each node's parents at construction, and a node keys its chunks by the pull time only where that holds. A graph with nothing time-varying in it therefore keeps one entry per tile however many instants are pulled, and never confronts its sources with a time they do not understand. RFC 3339 lives with `StacSrc`, the only element that speaks it, the engine core carrying numbers.

- Batch is a degenerate pull: enumerate the chunk grid over an extent (`materialize`, or the pyramid example's tile loop) and pull everything.
- Live is invalidation plus re-pull: `Engine::invalidate` walks a dirty window downstream (widened by each element's `spread`, projected across CRS changes), drops overlapping cache entries, and publishes `Invalidation` events for drivers to re-render.
- Serving is a driver too: `geoplumb-server` builds one engine per layer from a TOML file (source plus an ordered op pipeline, ending web mercator and an encoder the request picks), and `GET /tiles/{layer}/{z}/{x}/{y}.png?t={start}/{end}` turns the query interval into the pull time, so a layer's instant is a request parameter rather than a deployment. A path ending `.tif` hands back the same tile as a GeoTIFF carrying every band at f64 instead, the suffixless and `.png` paths staying the gray PNG. The served surface is a subset of what follows: a source is `stac`, `cog`, `geojson` or `las`, and `OpConfig` has fourteen variants. Nine are every single-input raster transform the crate ships, `hillshade`, `bandmath`, `slope`, `aspect`, `focal`, `mask`, `reclassify`, `unary` and `convolve` (which adds the raster to tensor, 3x3 convolution, tensor to raster chain as three transforms). `rasterize` burns a constant or a numeric property per feature, `idw` grids a point cloud into a raster band, and `vec_filter`, `vec_schema` and `vec_clip` rewrite features before a `rasterize` turns them into pixels. `deny_unknown_fields` holds over all of them, so naming any other element in a layer file is a parse error. A layer names either one `source` and one chain over it, or a list of `input` entries each with its own chain, a `fanin` of `mosaic` or `combine` (whose `op` is one of terrano's six binary operators) joining them, and a chain after the join. A `geojson` source needs a `rasterize` in the chain over it and a `las` source needs an `idw`, which the parse checks rather than leaving to the first tile. The in-memory GeoTIFF source, the tensor elements and the explicit reprojects stay unreachable from a layer file. The gray range the PNG stretches over comes from the last op that fixes one, or from the layer's own `gray = { min, max }`, which a layer ending in `reclassify`, `rasterize` or `idw` has to name because class numbers, burned values and interpolated point heights carry no range of their own, as does a fan-in layer nothing after the join fixes a range for. Everything else described below is reachable only from Rust code building a `Graph` against the crate.
- Event-stream processing (per-event latency, geofencing) is out of scope, that is fluvius.

## Caps negotiation

Adapted from glass2glass's CSP design (`crates/geoplumb/src/caps.rs`, `crates/geoplumb/src/solver.rs`, MPL-2.0). Elements declare a `Constraint`:

- `Produces(CapsSet)` — source shape
- `Identity(CapsSet)` — pass-through, optionally narrowing
- `Derived { input, passthrough, output }` — output derived from input, declarative: a `FieldMask` names the fields copied across, the override pattern pins retargeted fields (reproject pins `crs`)

Caps are kinded: a `CapsPattern` is a raster pattern (dtype, bands, crs, resolution range, chunk px), a point cloud pattern or a vector pattern (both crs, resolution, chunk px), or a tensor pattern (dtype, channels, crs, resolution range, chunk px), and cross-kind intersection is empty, so a link always negotiates to one kind and a point source wired straight into a raster consumer fails with the usual empty-link error. A `Derived` whose output pattern has a different kind than its input is a cross-kind transform (`IdwGrid` takes points and makes a raster, `Rasterize` burns features into one, `ToTensor` and `ToRaster` cross the tensor boundary either way). Its passthrough mask projects the fields every kind shares, crs, resolution and chunk size, which is what lets a crs demand downstream of a gridder narrow the point link, and lets the raster-side reproject auto-plug fire downstream of it. The bands mask bit projects as a plane count where both kinds have one, raster bands to tensor channels and back, so a single-band consumer downstream of `ToRaster` narrows the channel count and a mismatched chain fails at solve time instead of emitting bands its caps never promised. Each field of a pattern is a `SetField`: `Any`, an exact `OneOf` in preference order, or `AtLeast`, an open lower bound for the fields where order means something. It intersects a `OneOf` by filtering the set to the values at or above the bound, another `AtLeast` by taking the larger bound, and fixates to the bound when nothing narrowed it to concrete offers, which is how `BandMath` demands the band count its expression reads without enumerating a ceiling. A new kind extends the pattern enum and the common-field projection, the solver stays kind-blind.

`CapsSet` is preference-ordered alternatives of patterns. The solver alternates forward sweeps (narrow each output link through the node's constraint) and backward sweeps (consumers narrow producers, coupling backward through `Derived` only on passthrough fields) until the links stop changing: a fanin couples its input links through the shared consumer, so one sweep each way is no longer complete. Fixation then assigns concrete caps source-first by backtracking search, because a diamond can leave branch preference orders that disagree, where greedy per-link fixation picks a jointly impossible combination. The greedy choice is tried first, so chains and plain fan-out fixate as before. Failures are structured and name the link.

A fanin declares one `Constraint` that applies to every input link and the output link alike, so all pins negotiate to matching caps.

An empty link is not always a failure. The graph carries a registry of `Adapter`s: a template constraint with the element's retargeted fields left free, plus a factory. On a failing link the solver checks each adapter generically, `template.output_set(offer) ∩ demand`, and splices the built element when the bridge is nonempty, so the solver never knows which caps field an adapter fixes. `Graph::new` registers a reproject per kind, raster and vector (both bridging crs, the target being whatever the demanding side prefers, at a fanin the first parent's), and each declines the patterns of the other kind, so a failing link picks the one that fits it. `register_adapter` adds more. Spliced nodes are appended after their consumers, so the engine and solver walk `topo_order` rather than index order.

Divergences from g2g, deliberate:

- Resolution stays a range on fixated caps and is resolved per pull by ladder snapping, because in a pull engine resolution is request-time, not negotiation-time.
- Field coupling is declarative (masks) rather than closure-based. Geo caps fields are independent enough that the closure machinery and passthrough probing are unnecessary.

## Chunks and snapping

Requests snap to a per-node grid: a power-of-two resolution ladder anchored at the node's origin (`GridSpec`), tiled at the negotiated chunk size. Cache keys are `(node, level, ix, iy, time)`, the time being the pull's at a time-varying node and `None` at every other, so time variants of a chunk live side by side without costing a time-invariant graph anything. A request finer than the ladder base clamps to level 0 and the driver upsamples, coarser requests snap to the finest level that is at least as coarse. The ladder is not unbounded: `snap_level` clamps at `MAX_LEVEL`, 31.

Chunks are self-describing (`RasterChunk`: bands, resolved bbox, resolution, crs) because responses are addressed by request, not stream order, and snapping may widen the window. `Chunk` is an enum over kinds: `Raster`, `PointCloud`, `Vector` and `Tensor`. A point chunk is the points inside one tile window, thinned for its ladder level, and point tile membership is half-open (x in `[min, max)`, y in `(min, max]`, the top edge inclusive because tiles step down from the origin) so a point on a seam belongs to exactly one tile. A vector chunk is feature fragments clipped to the tile window: each fragment carries the source feature's stable id (shared by every fragment of one feature, so a later dissolve can reassemble seam-split features) and its full property map. Points and lines use the tile membership convention, lines splitting into parts where they leave the tile and a part lying entirely on an excluded edge going to the neighbour that owns it, polygon rings clip independently against the tile rectangle (Sutherland-Hodgman, exact float math), which keeps even-odd fill correct for pixel centers inside the window. Multi geometries and geometry collections clip member by member and stay one fragment holding whatever survived, dropped only when nothing does. A tensor chunk is a contiguous CHW block of f32 over the tile window: channel-major, and inside a channel row-major with rows growing down from the top of the bbox, the raster order, so its length is always channels times the window's pixel count. The same pull, cache, coalescing, spill and invalidation machinery serves every kind, only assembly differs: rasters and tensors mosaic, point chunks concatenate and filter, vector fragments re-clip, concatenate and sort by id so burn order downstream matches source order.

Each node's grid derives from its parent's through `output_grid`: identity for most transforms, a reproject anchors the canonical origin for known CRS (web mercator, wgs84) and estimates base resolution from the local scale. A fanin takes its finest input grid by default, and its elements sample inputs bilinearly onto the output grid, exact when an input shares the output alignment.

## Runtime

One map per engine is both cache and coalescing table: a chunk entry is `Ready` (cached, LRU by tick, byte-budgeted), `Spilled` (on disk only), or `Pending` (in flight, with waiters). Concurrent pulls of one chunk share the computation. A cancelled computer's drop guard removes its `Pending` entry and wakes waiters, one of which takes over, so cancellation never wedges a chunk. Errors are not cached.

The disk tier (`Engine::with_disk_cache`) writes every computed chunk through to a flat binary file and marks the entry spilled once the file is safely down, so memory eviction demotes to `Spilled` instead of dropping. A spilled hit reloads through the same pending machinery, coalescing concurrent readers. The disk budget counts cold bytes only and evicts files LRU. The store is a fresh subdir per engine, removed on drop, so files never outlive the caps and elements they were computed under, which is what makes persistence safe without an element identity hash.

Transforms' `compute` is synchronous by contract, the engine offloads it to tokio's blocking pool when a runtime is present and runs inline otherwise. Source `read` is async so ranged HTTP reads do not block the executor.

Engine caps are immutable per instance (solve happens in `Engine::new`), so cache keys need no caps fingerprint until re-solve exists.

## Elements

Thin wrappers over sibling crates: terrano-core for kernels and GeoTIFF IO, projicio-core for CRS transforms. The engine repo carries orchestration, not math. `BandMath` is the exception that carries its own: it parses a band expression at construction into an ast (band variables, f64 literals, the four arithmetic operators, the six comparisons yielding 1.0/0.0 at a precedence looser than arithmetic, unary minus, and sqrt, abs, min, max, pow, log, exp and a three-argument `where(cond, a, b)`) and evaluates it per pixel into a single output band, window-local on an identity plan, with nodata entering as NaN and NaN propagating through every operator: min and max included since `f64::min` would otherwise return the other operand, comparisons and `where` included so a nodata pixel never reads as an answer.

`QualityMask` and `Focal` are window-local raster transforms. `QualityMask` checks one quality band (sentinel-2 SCL, landsat QA) against a keep-list of codes and writes NaN through every band where the code fails or the quality band is nodata, band count and order unchanged, so downstream band indices stay stable. `Focal` computes mean, median, min or max over the square window of side `2r+1` per band, radius in output pixels, planning the upstream window wider by exactly the radius: the widened box is still on the node's own grid, so outward alignment adds nothing and chunked output equals whole-window output. A nodata neighbour drops out of the statistic, a nodata centre stays nodata. The terrain elements (`Hillshade`, `Slope`, `Aspect`) stay thin over terrano's kernels, `Aspect` in compass degrees, north zero clockwise, flat cells nodata.

Five elements implement `Source`. Three of them are raster sources, described here; `LasSrc` and `VecSrc` come further down with their kinds. `RasterSrc` holds the whole dataset resident and serves ladder levels by block-averaged decimation. `CogSrc` reads windowed over terrano's `CogReader`: each pull fetches only the tiles it touches at the file overview nearest the request, block-averaging the remainder when the file pyramid is shallower than the request. It serves every band the file carries, decoding each touched tile once for all of them and advertising the file's band count in its caps. Its transport is the `RangeRead` seam, with a local file impl in terrano and an async, multiplexed `HttpRange` here for remote files. `StacSrc` searches a STAC api at open to anchor its grid, crs and band count on the most recent item, then searches lazily per pull in two-degree lon/lat blocks kept in a bounded lru, so coverage follows the pulls instead of the open bbox. Every search follows the response's `next` links to the end, so `limit` is page size and never a coverage limit. Items whose declared band count differs from the anchor's are skipped, an item whose cog turns out to disagree fails the pull rather than being truncated. An item on another crs is kept with the anchor-to-item transform attached: its assets read the region covering the output window on the item's own pixel grid, then warp onto the anchor grid through the same inverse-mapped bilinear sampling `Reproject` uses, so a pixel at a utm zone boundary is identical whether a graph node or an item produced it, and same-crs items take exactly the unwarped path. Matched items' cog assets are lazily-opened `HttpRange` readers keyed by href (s3 hrefs rewritten to their public https form), and a pull combines the items covering its window according to the search's `Composite`. A search may name several assets for collections that spread bands across per-band cogs, sentinel-2's `red` and `nir` say: an item is kept only when every listed asset is present, the anchor's cogs must share one resolution, and a pull reads every asset, bands concatenated in asset order, so a downstream `BandMath` sees one multi-band raster. The default, `Latest`, mosaics them most-recent-first band by band: a pixel is complete only when no band is NaN there, so an older item can patch one band where the newest had nodata and leave the rest alone, and the walk stops as soon as every band is filled. `Mean`, `Median`, `Min`, `Max`, `Percentile` (0..=100 clamped, linearly interpolated between the neighbouring ranks), `StdDev` (population) and `Count` are temporal composites: they read every intersecting item with no early exit and reduce per pixel per band over the finite values, so nodata drops out of the stack rather than poisoning it and a pixel no item covered stays nodata, count included. `Mean`, `Min`, `Max`, `StdDev` and `Count` fold item by item into per-pixel running state, a count beside a running sum, extreme or mean, so each wave of item windows is dropped before the next is read and a pull's peak is one wave however deep the stack. `StdDev` runs Welford's method over that state, agreeing with a two-pass variance to precision rather than bit for bit. `Median` and `Percentile` need every value at a pixel at once, so they bound the stack spatially instead: the window is cut into horizontal strips whose pixels times stack depth times band count stay under a fixed value budget, and each strip is read, reduced and dropped before the next is read, so a pull holds the budget rather than every item's whole window. A window whose stack already fits takes one strip, which is the read and the reduce a whole window did. Strips are exact rather than approximate: the strip bboxes sit on the window's own pixel grid, so a same-crs item read for a strip is the same file pixels the whole window read, and an item on another crs takes its source resolution from the whole pull window, so two strips cannot land on different overviews and leave a seam. Time is resolved at the source by default and on the pull when a pull asks: `datetime` picks the interval, the composite picks what the interval collapses to, so "summer 2025 median" is a source configuration, and a pull carrying its own interval overrides `datetime` for that pull alone. Completed searches are cached by block and interval, capped at 256 entries and 8192 matched item references. Active pulls keep their results through eviction, and live items are shared by href across cached blocks and pull times so their pooled readers are too. The composite never moves, only the interval does. A whole collection then behaves as one raster with no local data, at any instant.

Two fanin elements. `Mosaic` takes the first input, wiring order, that has a value at each output pixel. `Combine` samples both inputs onto the output grid and runs terrano's binary op band by band.

The point cloud pair over nubis is the PDAL slot. `LasSrc` holds a cloud resident (LAS via nubis or in-memory), anchors its grid at the cloud bounds with base resolution estimated as the mean point spacing, and serves tile windows with per-level voxel thinning, one point per cell of the level's resolution, the point analogue of block-averaged decimation. `IdwGrid` is the cross-kind transform: it plans the upstream point window widened by its search radius (in output pixels, so every level sees a comparable neighborhood) and grids z by inverse distance weighting via nubis's windowed, radius-binned `idw_window`.

The vector pair over topoi mirrors it. `VecSrc` holds a feature collection resident (GeoJSON via topoi or in-memory), anchors its grid at the collection envelope with base resolution estimated as the median segment length, and serves tile windows by asking an R-tree over the raw-geometry envelopes which features can reach the window (exact, not a prefilter: Douglas-Peucker only removes vertices, so a simplified geometry stays inside its raw envelope and a feature whose envelope misses the window has no fragment of it to give), then simplifying those features whole (Douglas-Peucker at the level's resolution, deterministic, so every tile sees the same simplified geometry and seams stay consistent), dropping features whose envelope is smaller than a pixel (points and multipoints exempt, a collection measured whole so a small member rides along with a big one), then clipping to the tile. Level 0 is the raw geometry. `Rasterize` burns fragments to a single-band raster via topoi's `rasterize`, a constant or a numeric property per feature (features without it are skipped), last feature in source order winning where burns overlap. Its coverage rules (pixel-center fill, endpoint-independent line traversal) are preserved under clipping at pixel-aligned tile edges, so it needs no halo and chunked output equals whole-window output.

Three window-local vector to vector elements sit between the two, the head of a geodukt pipeline. `VecFilter` keeps the fragments whose property equals a value, `VecSchema` renames, drops and adds properties, `VecClip` intersects each fragment with a static boundary: polygons through topoi's overlay, lines cut at their crossings with the boundary rings and kept where the midpoint is inside, points by containment. All three run per fragment on an identity plan, so chunked output equals whole-window output by construction and none of them needs a halo. `VecReproject` is the vector twin of the raster reproject and the second registered adapter: it plans the inverse-projected window the same way, then forward-projects every vertex and re-clips to the output tile. Vertices only, no densification, so a long segment keeps its chord across the projection, the trade geodukt's reproject already makes.

The tensor trio is pure Rust and holds the model slot open. `ToTensor` scales and offsets raster bands into channels, `TensorConv` runs a 3x3 kernel per channel with one pixel of halo (a tap on NaN or off the window contributes zero, a NaN center stays NaN), `ToRaster` hands channels back as bands. The adaptation of the glass2glass model story is that a fixed model input size negotiates as a chunk size demand rather than an exact output shape: a consumer pinning `chunk_px` narrows every link back through both kind boundaries, so the tiles arriving at the model are the size it wants and everything upstream retiles to match. Growth is deferred until a consumer needs it: dtype is f32 alone, and layout is fixed CHW with no field to say so.

Zonal statistics and per-step time series are pull drivers beside `materialize`, not elements: every transform computes one tile of its own grid and only sees that tile, so cross-tile aggregation per feature id has to sit above the graph. `zonal_statistics` burns the features' ids over each tile of the window (geometry unclipped, topoi's pixel-aligned sub-window burn hitting exactly the pixels a whole burn would) and folds band 0 into mergeable per-feature accumulators: count, sum, minimum and maximum, with mean read off them and median absent because it does not merge. One tile is resident at a time however wide the window. `zonal_time_series` runs one pull per caller-supplied interval and reduces each step the same way, and `window_statistics` / `window_time_series` are the featureless variants over the whole window.

Zones are burned in request order and the last one wins a pixel two of them cover, the rule `Rasterize` already follows. Overlap is therefore resolved, not rejected: a zone contained in a later one reduces to an empty row, count zero and null statistics, and a zone containing a later one keeps only what the later one left. Every covered pixel counts once, for exactly one zone, so the rows of an overlapping set still sum to the union rather than double counting it.

## Known limits

- The zonal endpoints bound one request by validation (pixels summed over steps, features, steps, ring positions, and axum's 2 MB body) and the service bounds how many run at once: four reduction slots, a request finding none free refused 503 naming the cap before an engine is touched, and a reduction outrunning four minutes answered 504. Four minutes sits under the five a proxy in front of the service typically allows, so a slow caller gets this reason rather than the proxy's. The slot belongs to the blocking reduction, not to the request: a reduction is a `block_on` on the blocking pool and cannot be cancelled, so a timed-out request keeps its slot until the work really ends and the next request is refused rather than stacking another one on the pool. The wait is bounded, the work is not. These live in `geoplumb-server` rather than in a proxy in front of it so a direct caller and a differently deployed instance get them too, which leaves what a proxy is actually for uncovered: there is no per-client rate limit and no connection cap, one caller can hold every slot, and the limits are per process, so N replicas allow N times the concurrency.
- The disk tier lives and dies with one engine instance. Cross-process reuse needs an element identity hash so a graph edit cannot serve stale files.
- `CogSrc` serializes range reads on its file behind a mutex. `StacSrc` pools readers per asset instead, opening another when concurrent reads contend, so it does not. `StacSrc` keeps only items sharing the anchor item's per-asset band counts, and assumes same-crs items, and assets within an item, share the grid alignment (mismatches land on the nearest pixel). An item's lon/lat footprint converts to the anchor crs, and a pull window's bbox back to lon/lat, through a densified envelope, sixteen segments per edge, so a rotated cross-zone quad keeps the far side two opposite corners alone would cut off and a window's tilted corner names every block it overlaps. Sixteen segments hold that envelope to the metre against a walk 256 times finer, up to a window a thousand kilometres across; a bbox containing a pole is the case no edge walk covers, since the pole itself lies on no edge. A search stops at 1000 accumulated items and a pull at 32 cold block searches, both failing rather than mosaicking thousands of items, and both applying per pull time the way they apply per source. `Median` and `Percentile` hold every intersecting item's values over one strip of the window at once, so depth costs latency rather than memory: the strips run one after another, and a stack deep enough to need several of them takes that many passes of read latency, over the same distinct bytes since the tiles two strips share come from the range cache. An absurdly wide pull interval still reaches an absurd item count the way an absurdly wide `datetime` does. The item list does narrow per strip: a strip reads only the items whose footprint reaches its own rows, and a strip no item touches is filled as an empty window with no fetch at all. Item reads run in parallel, capped at 64 in flight across every pull in the process, `Latest` and the folding reducers reading in cap-sized waves, so `Latest` keeps its early exit and a fold peaks at one wave. What still grows with the item count for every composite is the per-item search metadata and reader pools, tens of kilobytes an item against a window's megabytes. Assets within an item are still read sequentially. `HttpRange` dedups fetches through a process-wide lru byte cache (256 MB, compressed bytes as fetched, single-flight on misses): cog readers request an interior tile as the same exact byte range every time, so the concurrent chunks of a pull, and neighbouring pulls, stop re-fetching the tiles they share. Fetches are async and multiplexed on a small dedicated runtime, `read_ranges` fetching a window's tiles concurrently under a process-wide transfer bound, so fetch concurrency does not cost a thread per transfer. A cold pull is now bound by the link to the data: distinct bytes over path bandwidth plus a few latency waves. Serving from the data's region is the remaining lever, not more client concurrency.
- Invalidation spread uses the coarsest cached level per node, over-invalidating slightly, never stale. It retains on the chunk bbox alone, so a dirty window drops every time variant of the chunks it overlaps, over-invalidating in the same direction.
- `LasSrc` holds the whole cloud resident and rescans it per tile read, there is no windowed LAS reader yet. `IdwGrid` grids only z, intensity and classification ride along in point chunks but no element consumes them.
- Tensors are f32 and CHW only, and there is no inference element: running a model belongs outside this repo, the engine's job ends at handing it windowed tiles. Each chunk is convolved on its own, nothing batches tiles across a pull.
- A line lying exactly on a pull window's max_x or min_y edge belongs to the neighbouring tile and is excluded from the window, the same rule a point there follows.
- `VecSrc` holds the whole collection resident and re-simplifies its candidate features per tile read. A polygon edge lying exactly on a tile seam clips to a zero-area sliver in the neighbouring tile: harmless to a burn and to a dissolve, visible to anything that counts fragments. A segment passing exactly through a cell corner is a float tie and may burn one corner-adjacent cell differently between chunked and whole runs.
- A whole-window vector pull returns clipped fragments, and `VectorChunk::dissolve` merges them back per feature id. It is a call for pull drivers and sinks, not a graph element, because no element can do it: every transform computes one tile of its own grid, an identity-plan element is handed exactly the fragments of that tile, and whatever it returned would be re-clipped to the tile anyway. Merging is not bit-exact either way. Polygonal fragments go through topoi's overlay, which snaps vertices, so a merged ring equals the source geometrically but not bit for bit. Line stitching matches endpoints within a few ulps: adjacent tiles solve the same Liang-Barsky ratio for a seam crossing, but re-clipping rebuilds a kept endpoint as start plus (end - start), which can land an ulp away.
